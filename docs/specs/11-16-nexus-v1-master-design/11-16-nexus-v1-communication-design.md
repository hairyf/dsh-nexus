# 03 统一通信与问答

状态：用户已批准（2026-11-16）。日期：2026-11-16。

总纲：[dsh-nexus 一期总纲](./11-16-nexus-v1-master-design.md)。依赖 [01 账本与策略](./11-16-nexus-v1-ledger-policy-design.md)、[02 运行编排](./11-16-nexus-v1-runtime-design.md)。本 Spec 拥有模型可见通信契约及问题生命周期，领域授权与持久不变量仍归 01。

## 目标与范围

只保留两个 Nexus 通信动词：ask 与 send_message。不再按角色同时暴露 report、reply_channel、send、answer、ask_user 等重复通信入口。管理操作、查看、取消、派工、重试、等待仍是独立能力，不为了减少工具数量变成消息正文命令。

本 Spec 包含 Nexus 自有角色的工具适配、地址解析、正式答复、升级与恢复关联；不实现 GitHub 网络协议或 Web 组件，也不改 DSH 原生子代理协议。工作会话复用 dsh-better-dsh 的编码预设能力；不把它换成只有自定义工具的阉割工作会话。

## 输入、输出与地址边界

### ask

新问题输入须包含实际问题内容；可使用现有问答交互中的题目、选项、多选、标题与 detail 补充信息。工单关联从可信角色绑定获得或明确给出并校验，不接受伪造角色/人工身份。

- 每次问题产生稳定 askId，返回受理身份及当前 pending/已答状态；未获得有效答案时不能返回默认批准。
- 提问等级、重要决定和合并策略按 01 统一判定，不由调用者任意指定一个更宽松的处理者。
- 合并 ask 明确关联工单、PR、目标分支、head 与验收依据；没有这些依据的普通问题不能触发合并。
- 上交已有问题时显式引用 askId，保留原问题和题目关联，不复制一份新问题。当前合法处理者可按 01 上交并补充上下文，不改写原始授权范围。
- 主执行 worker 可由绑定推导本票；project/supervisor 的工单问题须明确受影响工单。main 无票分诊 ask 仍直接到用户。
- 若复用多题表单，正式答案须保持题目关联，不能将局部答案或某个默认选项冒充整次批准。

### send_message

保留公共 message 文本，并区分以下互斥地址族：

| 地址族 | 契约 |
| --- | --- |
| DSH 原生代理 | 保持现有 agent_id + message 参数和 messageId 回执；直接复用原生父子权限与投递语义 |
| Nexus 普通消息 | 显式 to，区分 Nexus 角色/工作会话与已关联渠道地址；不能用任意字符串猜建会话 |
| Nexus 正式答复 | 显式 askId；收件者由原问题决定，不能再给出冲突地址或原生 agent_id |

同时提供不相容地址、未知地址或越权范围须报错；不隐式回落成公开发言，也不默认广播给所有角色。工具返回回显已解析的目标及受理结果，不能将入队说成已发送或已处理。

普通消息可以承载结构化 progress、ready、failed、dropped 及交付证据；插件消费结构化事实而不是猜散文。验收结论须明确关联验收要求、证据与有权判断者，交由 01 核定，不能提供一个可任意写 Ticket.status 的通道。子代理的技术结果不是主 Worker 的验收结果。

渠道权限仍按角色与工单范围收窄；统一工具名不扩大 Supervisor 的对外发言权，也不允许 Worker 写入无关话题。Nexus 外部消息遵循既有中文、简短、原位更新、不刷屏的沟通规范。

## 正式回答与升级

1. 模型正式回答通过 send_message 显式关联 askId；Web 表单与 GitHub 适配器转换为相同的答复语义，不把来源原文冒充已批准事件。
2. 验证当前处理责任、人工要求、工单范围、策略与目标版本后，一次性写入答案、实际身份和回送消息。成功表示已受理答复，不表示发起会话已经运行。
3. 首个合法答案生效；重试同一已受理动作不重发，另一份答案不得覆盖。第二入口看到现有结果，保留清晰的已解决/冲突反馈。
4. 普通 send_message、引用文字、超时默认值、工具退出或源消息的 user 角色字样均不是批准。没有 askId 的“同意”不能按某条碰巧 pending 的问题猜测关联。
5. 升级只迁移同一 pending 问题的责任。原处理者不能在已上交后抢答；Web、GitHub 都显示相同最终状态。
6. 显式撤销问题记录原因并撤下可操作入口；回合取消、项目暂停、暂时离线不等于撤销。已答/取消/目标已失效时给出可区分结果。

合并规则以 01 的三态策略为准；不能用普通汇报或模型自报的人类身份绕过 human_required。问题分级决定谁处理，不会赋予超出工单范围的执行许可。

## 异步、打断和等待

ask 的待决责任属于账本，不属于一条活着的调用栈。

- Nexus 工具必须异步并响应打断。未答时允许返回明确的 pending + askId，让宿主保存挂起工作线；不能占住项目编排整个回合，迫使其他票等同一个问题。
- Worker 不得因为收到 pending 就继续受该决定约束的动作；无关且已授权的工作不必被误当作全部取消。
- 打断当前等待只结束这次等待，原 ask 继续存在；后续有效答复由 02 唤醒对应工作线，并携带原关联，不让人重新回答。
- 新会话重试、重启或晚到答复不能重复建相同问题/执行相同已受理决定。发起方已结束或目标已变时，明确交给责任编排者处理，不能盲注入已失效会话。
- 超时只能表示 pending、中断、提醒或错误，不可产生人类答案。dsh-better-dsh/better-ask 的倒计时与默认回答也必须受此约束。
- 提醒计时、上级通知与故障恢复由 02 担当；本模块提供问题状态与责任，不通过模型反复 wait 轮询。

## DSH 与 dsh-better-dsh 兼容边界

当前安装基线为 DSH 0.2.2-rc.1；不以升级到 next 作为一期前提。原生 send_message 只返回 inbox 受理，无 Nexus ask 生命周期；原生 ask_user_question 受 live root 限制，不能充当多层问答的薄包装。

- Nexus 角色工具只安装到可信登记的 Nexus 自有角色会话。仅同名 preset 不表示归属；原生 helper、复用的 sidechat 不被当作工单主 Worker。
- 原生 helper 保留 DSH 带内部标记的 send_message、父代理回报指引和完成通知去重；不在其 scope 注入 Nexus 同名定义。角色身份与回报指令也依据可信绑定，不能仅因继承 worker preset 就要求 helper 调用它并不存在的 Nexus 工具。
- Nexus 父代理仍能通过 agent_id + message 继续原生子代理，原生分支不制造 Nexus Inbox/Ask，也不复制原生权限判断。
- 每个作用域同名只注册一次；旧角色通信工具不能与新入口长期并存。不能依赖错误的“后注册覆盖”假设。
- 保留标准 subagent/fork/list/interrupt 等既有工作能力；原生子任务完成通知与 Nexus 结构化报告不同，不重复计为两次交付。
- 复用 better-dsh 的编码工具、预设纪律和问题呈现能力，不为此另造问卷引擎；但待答状态、升级、身份与恢复由 Nexus 持有。

[当前注册入口](../../../src/index.ts)仅按 preset 匹配是现存风险；本 Spec 要求修复可观察行为，不规定某个私有注册实现。

## 与渠道及 Web 的交互

- [04 GitHub](./11-16-nexus-v1-github-design.md)将可信源身份、明确问题引用与答案交到本语义；本模块不读取 GitHub 评论来猜 actor。
- [05 Web](./11-16-nexus-v1-web-design.md)呈现同一账本状态、近况与侧聊入口；打开侧聊不自动回答原 ask。
- GitHub/Web 多入口是一个问题的不同表面，不是多个互相 race 后各留一份答案的系统。
- 发布失败不丢 Web 待答问题；回答后外部状态更新失败也不撤销已成立的答案，而是显示同步故障并恢复投递。

## 错误语义

需区分参数/地址冲突、目标不存在、调用者无归属、跨范围、非当前处理者、必须人答、策略/目标变化、问题已答/取消、发起方不可恢复及投递失败。失败不得半结清问题、半授权合并或静默新建收件者。

原生代理分支沿用 DSH 的错误与受理语义，不因 Nexus 存在吞掉越权或未知目标错误。取消后已经发生的外部副作用不能假定回滚，须按 02/04 核对。

## 独立验收与验证范围

- 四种 Nexus 角色只看到统一通信入口，普通消息不授权、不改任意工单状态；结构化汇报保留证据。
- 新建、待答、升级、正式答复、取消、重复答复、跨渠道竞答、策略变化与交付目标变化使用真实账本行为验证。
- 项目经理有一个未答 ask 时仍可处理另一票；打断后原 ask 可被晚答并准确续接；暂停不被答复解除。
- 验证选项、多选和 detail 不因上交/跨端而丢失，默认答案不能满足 human_required。
- 原生 helper 的 send_message 定义、回报指引、parent→child 继续、child→parent 结果与完成通知不被破坏；侧聊不被登记成主 Worker。
- 模块测试可隔离 DSH/渠道边界，但必须测实际 Nexus 实现与临时账本，不复制权限算法当期望值；真实 DSH/模型/渠道闭环由 06 验证。
