# 04 GitHub 接入

状态：用户已批准（2026-11-16）。日期：2026-11-16。

总纲：[dsh-nexus 一期总纲](./11-16-nexus-v1-master-design.md)。前置依赖：[01 账本与工单策略](./11-16-nexus-v1-ledger-policy-design.md)，可与 [02 运行编排与恢复](./11-16-nexus-v1-runtime-design.md)并行实现。

## 目标与边界

让已启用项目通过 GitHub 接收新工作线索、跟进工单、向人提问，并如实记录 PR 与 CI 事实。GitHub 是领域账本的输入输出适配，不是第二套工单、授权或问答系统。

一期使用 gh api 和用户显式选择的现有 gh 登录环境，配合当前 DSH Web。不开 OAuth、GitHub App、webhook、其他 IM，也不建立跨渠道账号统一系统。

本 Spec 负责来源识别、轮询采集、文本问答协议、发布关联、外部写入与结果核对。01 唯一拥有共享领域契约、白名单、策略及状态不变量；本 Spec 不复制提问等级与合并策略表。

不负责模型分诊判断、工单派发、会话恢复或 Web 布局。[03 统一通信与问答](./11-16-nexus-v1-communication-design.md)提供消息与 ask 领域流，但不是本适配的前置实现依赖。

## 接入环境与职责

- 接入前明确展示所选 GitHub 站点、gh 登录账号和目标仓库；仓库身份来自 01 的项目登记，不从面板显示名、正文链接或模型参数猜测。
- 只复用该环境已有的凭证来源；不采集 token 表单，不将 token 写入 Nexus 数据库、日志、模型上下文或错误详情。
- gh 不存在、未登录、账号不符或仓库不可访问时，接入保持不可用并说明原因；不自动切换到其他登录账号或站点。
- 登录账号负责发起 API 调用，不因此成为人工批准者。即使它在白名单中，已知 Nexus 出站回流仍不是人的答复。
- 项目禁用或失联后停止自动处理与新的外部写操作，保留历史、游标和发布关联；恢复时核对后续接，不把旧数据重新当首次接入。
- 网络调用必须可中断；中断、超时及进程退出留下的未知写入结果，在恢复时核对，不直接宣告失败并重发。

账号或环境发生变化必须重新明确选择并核验访问能力。更换登录环境不重置工单、来源身份或已答问题，也不迁移、复制任何凭证。

## 输入输出与责任分界

适配输入是已登记项目与仓库、当前白名单、话题订阅、待发布消息/ask、发布关联以及经过 01 核验的外部动作请求。不能以任意 URL 或文本代替已解析的领域目标。

适配输出包括稳定来源身份的 Trigger、上下文 Message、候选正式答复、Outbox 投递结果，以及具体 PR/head 的远端事实。答复是否结清、是否派工、是否满足验收，由领域与编排责任方判断。

- 新话题线索交 main 分诊；入队不等于建票或授权执行。
- 已订阅话题的新评论、PR 更新和 CI 事实关联原工单；多票订阅时保留各自关联，不任选一票代表全部授权。
- 候选正式答复归一为显式关联 askId 的 send_message，保留提供方用户身份、来源事件及正文，交 01 的核验与一次结清边界；不能先写一份渠道答案再异步同步。
- GitHub 投递失败、读取中断和未知结果均成为持久可见事实，供 02 提醒及 [05 Web 面板与信箱](./11-16-nexus-v1-web-design.md)展示。
- 03 消费同一消息/ask 流，不改变本 Spec 的身份识别与 GitHub 文本规则；独立验证可直接提供符合 01 的输入并检查领域输出。

## 来源身份与准入

话题身份包含 GitHub 站点、规范仓库身份和 issue/PR 资源身份。仓库甲的 12 号不能与仓库乙的 12 号混同；PR 的 issue 评论与其 PR 事实归同一话题，但事件种类和远端事件身份仍区分。

来源记录保留提供方事件/评论身份、作者用户 id、login 快照、创建及更新时间、话题和必要远端链接。评论编辑属于原评论的新修订，不是另一个作者或另一个话题。

GitHub login 按 01 大小写归一核验，白名单是唯一授权名单，不读取 write、maintain、admin 或仓库成员关系来扩大资格。每次新授权与正式答复都使用当时的白名单。

- 白名单人员在接入基线之后创建的新 issue/PR 自动进入 main 分诊，不要求 @ Nexus、专用标签或固定开头。
- main 判断它是新任务、已有任务补充还是无需行动；适配不能因标题像命令就直接派发 Worker。
- 已关联工单的 issue 评论、PR 主讨论及评审评论、PR 状态和 CI 更新自动跟进，不要求每次重新 @。
- 非白名单人员的协作内容可进入上下文，但不能直接授权新工作、变更目标或批准 ask。后续由合法责任方决定是否采纳。
- GitHub 标记的机器人、已知自动化身份，以及通过发布关联识别的 Nexus 出站消息均不得冒充人；外观像人的账号不能绕过已知出站识别。
- 引用、代码块、复制的批准语句和正文自称管理员均只是内容，不能替代可验证的作者身份。

从白名单移除人员不删除历史审计；其旧留言不能在移除后被重放为新的有效批准。话题归属不明或仓库与项目映射冲突时明确等待处理，不自动挑选项目。

## 首次接入、增量与历史

首次启用为每个仓库建立可恢复的采集基线，区分接入前的历史与接入后的新事件。建立基线不生成一批历史工单，也不能以“首次轮询”把已有 issue/PR 全部当新任务。

已关联话题按需要补取正文、相关评论、PR 与当前 head 的检查结果，标明为历史上下文，不伪装成刚发生的授权事件。历史补取不重放已结清的 ask，也不覆盖已有答案。

基线建立期间发生的新建话题和后续事件不能丢失：采集范围应覆盖基线边界，利用稳定事件身份消除重叠。接入前旧话题的普通更新不自动成为新任务；新工作的判断仍走 main 分诊与授权边界。

增量读取覆盖分页，不能只读第一页、最新若干条或只读开放话题；已关联 PR 的关闭、合并及后续检查也必须被发现。必要历史补取有明确话题与目的，不无限回放全仓库。

- 每个仓库、资源流分别保留已确认的进度；时间戳相同、页间重叠和编辑重排不能漏事件或重复触发。
- 只有相应事件可靠落账或明确归为已处理后才推进进度；分页中途失败保留可续读边界，不越过未处理内容。
- 来源去重依远端稳定身份与修订事实，不依正文相同或 issue 号码；不同作者的相同文字仍是不同事件。
- 重复轮询、进程重启及网络重试不重复建分诊候选、结清问题或向同一收件责任重复注入消息。
- 同一评论的后续编辑可更新上下文；已成功受理的正式答案不随评论编辑而被覆盖，修订历史保留审计依据。
- PR/CI 事实携带实际 head 和采集时间；旧 head 的成功检查不能冒充新 head 的通过，乱序结果不能回退当前事实。

删除或不可访问的资源保留已知来源与原因，不把读取失败解释为内容为空、工单取消或 PR 已合并。

## GitHub 文本问答协议

需要人回答且有 GitHub 来源的 ask 在对应 issue/PR 的 Nexus 受管评论展示，同时始终进入 Web 汇总。没有 GitHub 来源的问题不凭空公开到任意仓库。

每个问题展示完整 askId、问题、必要选项、所属工单和当前状态；合并问题还展示具体 PR、目标 base 与 head。只公开回答所需信息，不自动公开内部会话日志、凭证或与该话题无关的工单内容。

正式回答采用一种最小文本格式：评论中独立一行以“回答 ”开头，随后是完整 askId、中文或英文冒号及非空答案。例如“回答 ask-123：选择 A”。Nexus 发布问题时同时说明这一格式。

- 只有上述顶层回答行是候选正式答复；普通“同意”、反应表情、关闭 issue、PR review 的 APPROVED 或引用问题均不自动成为 Nexus 批准。
- 引文和代码块中的回答行不生效；缺少 askId、答案为空、格式不明或 askId 不存在时不猜测关联。
- 一个评论可用独立回答行回复多个 ask；每行只绑定一个完整 askId，各自核验并报告结果。同一修订对同一 ask 给出多条互相冲突的答案时，拒绝该 ask 的回答并反馈，不猜一个批准。
- 回答必须位于该 ask 已发布关联的同一仓库话题，且 ask 仍待答、当前允许该人回答；在别的话题粘贴有效 askId 不能借此授权。
- GitHub 作者身份由远端返回确定，不接受评论正文自报用户；核验当前白名单、人工要求和关联工单策略后，才可提交正式答案。
- 用户可编辑自己尚未被受理的评论补成有效格式；已结清或取消的 ask 不因后续编辑重新打开，答案更正必须走合法的新决定而非静默覆盖。

Web 与 GitHub 指向同一 ask，一处有效回答即全局生效。并发回答只有一次结清成功，另一处展示已回答及来源；重复事件不得覆盖首个答案，也不得要求人重复作答。

格式错误、非授权答复、已结清及目标变化均给出可区分结果。不能反馈到 GitHub 时，Web 仍显示该来源答复为何未受理，不能让用户只看到长久无反应。

## 受管评论、投递与提醒

同一话题由 Nexus 维护一条受管评论；后续问题、状态、答复结果和提醒原位更新，使用 gh api 的 PATCH，不为每次进展或提醒新增一条评论。人自己的评论不受此约束，也不由 Nexus 改写。

同一话题有多个待答问题时，受管评论列出多个清晰分隔的 askId、各自问题与状态。不能用一个含糊的“同意全部”代替逐个问题的正式回答或抹掉仍待答的问题。

受管评论同时保留必要的近期结论与来源，不承担完整日志归档。已回答条目可以精简为状态和答案摘要，但稳定 askId 与领域审计不得因版面精简丢失。

- 首次发布记录逻辑消息与远端评论关联；更新只作用于已核验属于 Nexus 的受管评论，不按正文相似度修改别人的评论。
- 同票同收件地址遵守 01 保序；多个工单共用受管评论时，更新不能相互覆盖丢问题，也不能让旧版本覆盖较新答案状态。
- 一处回答落账后，另一处的显示同步失败只记投递问题，不回滚答案或重新提问；恢复时更新到最新领域状态。
- 写入已知成功不重发；超时、断线或响应丢失先依据远端发布关联与可识别标记核对，不能盲目新增评论。
- 结果仍未知时保持待核对、保留原因并通知责任方；可识别标记仅用于关联，不是认证或授权凭证。
- 确认受管评论被删除且目标仍可写时，可恢复一条替代评论并更新关联；无法访问、权限不足不能假定为删除并反复重建。

提醒由 02 的宿主机制触发，本适配只更新原问题的提醒信息及投递事实，不创建新 ask，不因无人回答默认同意。重试上限与退避沿用 01 配置，不另设无限重试。

PATCH 编辑不保证触发 GitHub 通知，投递成功也不证明用户看过。Web 必须持续汇总未答问题、到期提醒及渠道失败，不能因 GitHub 更新成功就移除仍需人处理的事项。

## PR、CI 与合并外部动作

PR/CI 采集输出远端事实，不直接写工单成功。PR 关闭但未合并、检查失败、检查仍在运行以及外部已合并需要区分；Worker 自报完成或发来 PR URL 均不能替代实际核对。

合并是受 01 约束的外部写动作，不是收到“同意”就调用 API。适配接收已获有效决定的具体交付目标，执行前重新核对以下事实：

- 当前项目仍启用可用，站点、仓库、PR 身份与关联工单匹配，PR 当前开放且不是已合并对象。
- 当前 head 与许可覆盖的 head 一致，base 与许可覆盖的目标分支一致；新提交、改 base 或换 PR 均使旧许可不适用。
- 当前工单策略仍允许该决定，正式答案和回答者合法，验收证据覆盖当前交付范围；不复用另一工单或 PR 的批准。
- 仓库合并保护、必需检查、评审与当前 head 的 CI 要求满足；状态未知或检查尚未完成不是通过，不使用绕过保护或管理员强制合并。确实未配置必需检查与获取失败须区分；没有仓库检查也不能免去工单验收。

外部写请求必须约束所核验的 head；远端拒绝、head 不匹配或保护规则变化时停止该动作并回报变化，不偷偷换目标重试。必要的新决定仍通过同一领域 ask 流，不另建渠道审批。

合并请求被 API 受理不等于观测到实际 merged。结果未知先查询同一 PR 的真实状态；成功证据记录实际合并结果，随后交编排者完成领域验收，不由渠道适配直接宣告 done。

若 PR 已被外部合并，如实输出 merged 事实，不再合并一次，也不伪造 Nexus 历史批准。缺少有效交付决定时由责任编排者核验并按 01 处理；事实展示与批准有效性分开。

## 错误语义与可见性

以下情况必须能够区分，并保留项目、目标、操作、已知结果及可继续条件；错误详情不得包含凭证：

- 环境不可用：gh 缺失、登录失效、所选账号不符；等待用户修复选择或凭证，不自动注册新认证系统。
- 来源不可用：仓库/话题不可访问、分页失败、响应无法识别；保留进度与历史，明确哪些数据尚未核对。
- 授权拒绝：非白名单、机器人、出站回流、错误话题、未知 ask、已答/取消或当前策略不允许；不产生半截批准。
- 目标变化：head/base 不符、项目禁用、PR 已关闭、证据过期或保护未满足；保留原因，不把旧许可降格成普通成功。
- 暂时性故障：限流、服务端失败、网络中断；尊重远端重试提示及有界重试，不重复放大同一事件。
- 写入结果未知或持久化失败：先核对远端与账本；不能以空列表、成功回执或新增评论掩盖不确定性。

单仓库或单话题失败不能堵住全部项目。持续无进展、重试耗尽及不能回传的答复错误均留给责任编排者和 Web 汇总；未接通 GitHub 时问题仍在 Web 可答。

人工暂停期间可以记录相关新事实，但不能因评论、CI 或答复解除暂停。中断与恢复也不撤销既有 ask、吞掉来源事件或把未送达消息标为已读。

## 独立验收

1. 白名单新话题无需 @ 即产生一次 main 分诊输入；非白名单、机器人和 Nexus 回流不产生授权，仓库角色不会扩大白名单。
2. 首次接入不批量创建历史任务；已关联话题可获得必要历史，接入边界的新事件不漏、不重复，跨仓库同号严格隔离。
3. 分页、重叠轮询、同时间戳、评论编辑、重启及中途失败后，来源与游标可恢复；相关 PR/CI 更新不会错用旧 head。
4. GitHub 文本回答能明确关联 askId，错误格式或普通“同意”不获批；当前白名单与来源核验失败的结果可见。
5. 同一 ask 在 Web 与 GitHub 竞答仅一份正式答案；晚到、编辑、取消、重复及跨话题重放不能覆盖或误批。
6. 多个 ask 共用一条受管评论仍可分别回答；状态与提醒使用 PATCH，删除、断线与未知结果不会形成刷屏或丢失其他待答项。
7. GitHub 发布失败和编辑不触发通知时，Web 未答问题及到期提醒仍保留；投递成功不冒充已读或已处理。
8. 合并前复核 PR/head/base、当前许可、验收与仓库要求；新提交旧批准无效，结果未知可核对，外部已合并不伪造批准。
9. 项目禁用、暂停、权限失效、限流及中断均保持可解释状态，不启动未授权外部写入，也不阻塞其他项目。

## 独立验证范围与真实验证边界

适配行为测试使用真实 01 领域实现与隔离临时数据库，在 gh API 边界提供可控响应，覆盖身份、分页、去重、文本解析、落账、保序与错误。不能只断言请求字符串，也不能复制一份白名单或 ask 策略冒充领域实现。

不依赖 02 的真实调度、03 的工具实现或真实 Web 页面即可完成上述独立验证；以符合 01 的消息/ask 输入及提醒事件驱动适配，检查实际领域记录与发布结果，而非让模型猜审批结果。

真实 GitHub 验证使用用户允许的 omdsh-dev/dsh-nexus 测试话题与隔离测试分支。测试 PR 可以显式指定隔离的测试目标 base，不能默认指向仓库主分支；本 Spec 不授权写入或合并到 main/dev。

验证证据区分模拟边界与真实 gh api 结果，记录测试仓库、话题、head/base、答复来源、受管评论关联及实际合并结果，不暴露凭证。不能通过删除用户历史、重置真实配置或重复写评论来获得通过。

本 Spec 通过只证明 GitHub 适配与领域边界；真实模型、宿主唤醒、浏览器显示和整套交付链由 [06 宿主装配与真实验收](./11-16-nexus-v1-integration-design.md)核验。Spec 最终批准前不执行这些验证或外部写入。
