# 01 账本与工单策略

状态：用户已批准（2026-11-16）。日期：2026-11-16。

总纲：[dsh-nexus 一期总纲](./11-16-nexus-v1-master-design.md)。本 Spec 无前置实现依赖，是共享领域契约与数据迁移的唯一归属。

## 目标与边界

为自动分诊、执行、问答和验收提供同一份持久账本与授权判断。下游消费本 Spec 的领域事实，不各自维护一份工单状态、白名单、问题答案或权限副本。

本 Spec 包含项目、工单、角色绑定、话题订阅、依赖、消息、问题、投递和配置的持久语义；不实现 DSH 调度、工具适配、GitHub 网络连接或 Web 组件。沿用已有数据库与生成链，统一现有漂移，不另建通用工作流或身份平台。

## 现状与权威基线

当前 [目标 schema](../../../prisma/schema/project.prisma)、[运行时类型](../../../src/database/types.ts)与已应用迁移并不一致；例如 Project.channelId 的去留、remoteUrl/enabled 和并发默认值。已有工具声明不代表运行能力。

实现结果必须使目标 schema、迁移、生成类型、领域读写及新旧数据库一致。不能只生成新类型，也不能由各下游追加互相冲突的表。数据库应归属当前 DSH profile 的 Nexus 状态目录；不能依赖工作目录中的固定 data.db，也不能在纯模块导入时自动迁移真实用户库。

## 领域对象与责任

| 对象 | 对外语义 |
| --- | --- |
| Project | 一个已登记 Git 工作区/仓库；显示名不是仓库身份 |
| Ticket | 归属一个项目的工作目标、验收要求和执行授权 |
| 角色绑定 | main 全局唯一；project 每项目一个；supervisor 临时关联跨项目工单；worker 关联工单的一次主执行 |
| Thread / Trigger | 外部话题及不可混淆的来源事件；事件不是授权本身 |
| TicketThread | 工单订阅话题；与话题分诊归属分开 |
| TicketLink | 工单依赖/关联；依赖取消不等于依赖成功 |
| Message / Inbox | 一次被受理的消息及其收件责任；不是隐含派工或批准 |
| Ask | 有独立身份、当前处理者、策略依据及答案的待决问题 |
| Outbox / 发布关联 | 同一逻辑内容在外部渠道的投递及远端消息关联 |
| 验收记录 | 交付范围、证据、判断者与依据；不能只留一句完成文案 |

这些是共享业务概念，不要求为每个概念单独建表。表、索引和本地类型布局由实现决定。

Nexus 自有角色会话必须有可恢复的账本绑定。仅继承同名 preset 的原生 DSH helper 或侧聊不是工单主 Worker，不获得其授权，也不消耗一个新的主执行名额。每票同一时刻最多一个主 Worker；内部原生子代理不是另一张工单。

## 项目与授权范围

- 一期项目与 Git 工作区/仓库一一对应，不支持项目包含多个仓库或多个项目争用同一仓库归属。重复候选明确提示，不猜一个归属。
- 仓库身份由 remote 解析为托管站点与规范仓库身份，不从显示名推断。GitHub 同号 issue/PR 在不同仓库不能撞身份。
- 只自动处理用户已启用且仍可用的项目。发现、刷新不擅自启用新候选，不清除历史或重置勾选。没有历史选择的新候选默认未启用。
- 禁用/失联项目保留历史及订阅，不自动转给其他项目；不再派工、续跑或执行外部写操作。在途调用的打断与收尾遵循运行 Spec。
- main 管分诊与授权归属；project 管本项目执行；supervisor 管关联工单间的跨项目依赖；代码实现交给 worker。
- 建票、派工、停止、重试及协调范围变更是管理操作。普通 send_message 不隐含这些操作，更不能靠正文中的命令绕过它们。
- main 负责建票、归属与 supervisor 范围；project 只为本项目已授权工单建立主 Worker；supervisor 只协调/派发已关联工单，不直接建立 Worker。停止必须有明确人工依据，重试仍须保持既有授权。

普通消息的最小收发范围如下；正式答复另按 askId 当前处理责任判断：

| 发送者 | Nexus 内部目标 | GitHub 普通发言范围 |
| --- | --- | --- |
| main | 相关 project、supervisor | 已启用项目的已核实话题 |
| project | 本项目 worker、main、负责相关工单的 supervisor | 本项目已关联工单话题 |
| supervisor | main、关联工单所属 project，不直接联络 worker | 不直接对外发言；其 ask 按问题路由可交用户 |
| worker | 本票 project；原生 helper 通信沿用 DSH | 本票已关联话题 |

## 配置契约

以下名称是跨模块使用的配置契约，界面使用中文标签。

| 位置 | 键/值域 | 新安装默认值 |
| --- | --- | --- |
| 全局 | defaultQuestionLevel：detailed / important / automatic | important（仅重要信息） |
| 工单 | questionLevel：同上 | 创建时复制全局值 |
| 全局 | defaultMergePolicy：follow_question_level / human_required / automatic_allowed | follow_question_level（跟随提问等级） |
| 工单 | mergePolicy：同上 | 创建时复制全局值 |
| 全局 | GitHub 授权人员白名单 | 空，未配置不接受外部授权 |
| 全局 | maxWorkers | 4，与现存运行时默认对齐 |
| 全局 | backgroundLimitMinutes | 30，预算到期不是工单成功或批准 |
| 全局 | deliveryMaxAttempts / deliveryRetryCeilingSeconds | 3 / 60，退避起点沿用 2 秒 |
| 全局 | reminderIntervalMinutes | 10，正整数，属运行提醒而非授权超时 |

工单实际值落库，不在读取时动态回退到全局。后改全局只影响新票；修改已有工单的档位/合并策略必须是明确的人工配置操作，记录操作者、时间及变化。代理不能为回答自己的问题而放宽策略。

待答问题及尚未履行的合并决定受当前工单策略约束；配置变化不自动产生答案或批准。必要时重路由同一待答问题；已经不符合当前约束的代答不能继续执行外部操作。

不保留旧 autoMerge 布尔和行数阈值作为另一套暗中生效的授权系统。迁移规则见后文；仓库自身的检查与保护规则仍有效。

## 身份与白名单

- GitHub 只认显式人员白名单，不查仓库 write/maintain/admin 权限来自动扩充资格。配置使用 GitHub login，大小写归一；事件记录还需保存提供方用户 id 和 login 快照以便审计。
- 非白名单的真实协作内容可以作为上下文，不能直接授权新工作、变更目标或替人批准。机器人与 Nexus 已知发出的消息不能算人的答复。
- Web 的人工身份来自宿主现有认证/用户入口，不接受模型或客户端正文自报身份。不新做跨渠道账号绑定、多租户或新认证体系。
- 角色、会话、人工/代理来源由宿主绑定确定，不能由工具参数伪造。模型消息中的引文、system 字样或权限声明不是授权。
- 每次新授权或正式答复按当时的白名单/策略核验；已被移出白名单的人不能继续批准尚未结清的 ask。

## 问题路由与代答规则

| 发起者 | detailed 普通问题 | important / automatic 的上级链 |
| --- | --- | --- |
| worker | 用户 | 本工单 project |
| project | 用户 | 有负责本票的 supervisor 则交它，否则 main |
| supervisor | 用户 | 用户 |
| main | 用户 | 用户，main 发起的 ask 始终问人 |

上级收到问题不代表可以替人做决定：

- important：普通实现选择可代答；目标、范围、验收标准、对外承诺等重要决定最终交人。
- automatic：授权内的重要取舍也可代答；不能扩充授权范围，缺凭证/权限等不可代办条件仍找人。
- 重要性依目标和影响判断，不靠关键词冒充语义校验；预设要给出上述准则。合并请求是框架明确识别的重要决策，不依赖模型把正文标成重要。
- 工单相关 ask 必须能确定责任工单。若影响多张票，必须同时满足所有受影响票的权限；不能挑最宽松的一张替其他票授权。
- main 分诊阶段可有无票 ask，只问用户；不能以无票问题绕过已存在工单的策略。

### 合并策略优先级

| mergePolicy | 合并 ask 的可回答者 |
| --- | --- |
| human_required | 必须是经过核验的人，不受提问等级放宽 |
| automatic_allowed | 允许上级编排依据验收证据代答，即使提问等级为 detailed；不代表无条件同意 |
| follow_question_level | detailed、important 必须人答；automatic 允许上级代答 |

正常合并问题由执行工作线发起，上级不能自问自答伪造批准。main 自己发起的 ask 仍只能投用户。

合并许可只覆盖明确的仓库、PR、目标分支和待合并 head；提交变化后，旧批准不能授权新代码。不能将一次批准重放到另一 PR/工单。合并前还要核验当前策略、交付证据及仓库要求。

answered 不等于获准合并。合并问题必须提供明确的“允许合并”与“不允许合并”选项，只有显式选择允许、通过核验并绑定上述目标的答案才形成许可；拒绝、要求调整、任意自定义文本都不能默认转成允许。渠道可将对应选项编号/精确标签归一为此决定，不做模糊肯定词匹配。

目标实质变化时，未答旧问题明确取消，已答旧决定保留但不能履行；需要新决定则创建关联的新问题。它与“同一目标向上级升级沿用原 askId”不同，不通过改写已答问题绕过一次结清约束。

## Ask 与消息的共享不变量

- Ask 至少保留稳定 askId、关联工单/来源、发起角色、当前处理责任、问题内容、决策类型、策略依据、状态、正式答案及实际回答者/来源；合并 ask 还关联具体交付目标。
- 状态为 pending、answered、cancelled；升级是同一 pending 问题换处理者，不复制问题，也不先伪装成 answered。提醒不改变答案状态。
- 正式回答显式关联 askId，核验当前处理者与人工要求后一次性结清；并发或跨渠道重复回答不能覆盖首个答案。已经取消/结清的问题不能再次获批。
- 普通消息、投递回执、超时默认值、关闭通知、原生子代理的 settlement 都不能充当正式答复。通用标记已读/处理完不能关闭一个未答 ask。
- 回答记录与回送发起方的待投消息应一起可靠落账。答复已落账但发起者尚未恢复时不能要求人再答一次。
- 用户信箱是同一问题的视图；GitHub 发布副本只保存关联和投递状态，不维护第二份答案。
- 受理、投递成功、进入上下文、处理完成是不同事实。readAt 表示进入收件者上下文，不是入队时间。
- 同票同收件地址保序，不让一票阻塞所有项目；投递失败、等待处理与等待人分别可见。
- 中断回合不抹掉问题或未处理消息。显式撤销 ask 与打断当前等待分开，撤销必须有合法来源和原因。

## 工单状态与验收

保留 waiting、queued、running、review、done、cancelled 的领域区分；需人处理、故障、暂停从对应事实派生，不用一个状态覆盖所有维度。

- 建票须有项目、目标、验收要求及配置快照；分诊候选不混入已授权工单。
- ready/会话结束只进入待验收，不能直写 done。失败、PR 未合并关闭、后台超时不能冒充成功。
- 有 PR 的正常交付须有验收依据、有效合并 ask 决定及提供方实际 merged 事实。合并 ask 兼交付确认，不再重复问一轮。
- 外部已经合并的事实必须如实显示；若缺 Nexus 的有效交付决定，交给编排者核验，必要时走既定策略的确认 ask。不得伪造历史批准或再执行一次合并。
- 无 PR 成果由项目编排核验验收要求与证据，需人决定时按上述 ask 规则办理，不强造 PR。
- 明确的人类停止可产生 cancelled；单纯 PR 关闭、失败或终态票收到普通消息不等于新授权。继续工作须有明确的管理决定与现有授权依据。
- 人为暂停保留来源、时间与原因；评论、答复、CI 更新只新增事实，不自动解除暂停。
- 依赖只有成功交付才自动满足；前置 cancelled/失败须重新判断，不能释放后续任务冒充成功。跨项目依赖完成必须有持久唤醒依据，不只靠代理记得汇报。

## 投递、迁移与失败语义

逻辑消息和来源事件使用稳定身份去重；GitHub 话题身份包含站点、仓库与资源身份。模型提供的任意字符串不能建立真实收件人或授权关系。未知/越权目标拒绝且不产生副作用。

外部 API 的受理与落账可能不同时完成；已知成功不重发，结果不明先核对远端关联，不能靠盲目重试保证所谓端到端恰好一次。

迁移须满足：

1. 以现存迁移实际可产生的旧库为验证基线，同时统一目标 schema、生成物和读写模型；不得删除用户旧库来获得通过。
2. 历史未结工单补齐固定的 important + human_required，不动态继承新全局值。历史待答问题保留身份与来源，不把角色枚举 user 伪造成可验证的具体批准人。
3. 旧全局 autoMerge 布尔无法完整表达新语义，迁移为 human_required，不推导新的自动授权；新安装使用上表默认值，迁移结果在设置中明确可见。用户之后可明确选择自动策略。
4. 历史已结束记录保留，不补造新流程的验收或批准证据；新执行必须满足新不变量。
5. 消除 Project.channelId 等旧身份轴与新仓库身份的矛盾；保留历史订阅、来源、工单和会话引用，不按显示名猜迁移归属。无法确定的数据明确需要人工处理。
6. 迁移失败时不启动自动派工/外部写操作，给出原因；不留下半套已升级状态继续执行。

各入口对无效配置、项目禁用/不可用、目标不存在、无权限、策略变化、问题已结清/取消及投递失败给出可区分结果。拒绝操作不留半截批准/派工。不得吞掉存储或迁移错误，返回空列表伪装成功。

## 独立验收与测试范围

以真实临时数据库和领域实现验证，不以源码字符串或静态字段快照代替行为测试：

- 空库与实际旧结构升级后契约一致，历史引用不丢、不会获得新的自动合并权限，重复启动不重复迁移或建票。
- 三档提问 × 三档合并策略 × 四种发起角色的路由/可答判定；main 恒问人；工单快照与全局修改隔离。
- 白名单增删、代理伪造人工、非白名单/机器人/Nexus 出站回流不能授权。
- 升级身份不变；两渠道竞答仅一次成功；取消、重复、过期目标/策略变化不会误批；标通知已读不能结清 ask。
- ready、失败、未合并关闭、实际合并、无 PR 验收、外部合并缺决定、人工暂停和依赖取消的完整状态断言。
- 受理/读入/处理分离，未读移交、保序、失败持久化和不可用目标拒绝。

测试只操作隔离目录，不触真实 DSH home 或工作数据。本 Spec 的通过仅证明账本/策略边界，不声称真实 DSH、GitHub 或浏览器已经集成。
