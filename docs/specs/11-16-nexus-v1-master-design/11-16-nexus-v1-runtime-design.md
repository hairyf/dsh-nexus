# 02 运行编排与恢复

状态：用户已批准（2026-11-16）。日期：2026-11-16。

总纲：[dsh-nexus 一期总纲](./11-16-nexus-v1-master-design.md)。前置依赖：[01 账本与工单策略](./11-16-nexus-v1-ledger-policy-design.md)。本 Spec 定义角色运行、会话控制与恢复行为，供 [03 统一通信与问答](./11-16-nexus-v1-communication-design.md)消费。

## 目标与边界

让编排者按持久责任接收事件、推进工单，并在等待、打断和宿主重启后继续履责。模型可以空闲，不要求通过永久等待回合维持存活，也不靠反复查询制造进展。

本 Spec 包含角色会话绑定、派工与并发、独立工作区、异步工具、中断、事件唤醒、宿主提醒和恢复核对。项目、工单、ask、消息及授权状态只使用 01 的领域契约。

不定义 ask/send_message 的公共参数、正式回答或渠道投递协议；它们由 03 负责。不另建通用 job 总线、权限系统或侧聊隔离，不要求升级当前 DSH。

## 角色与会话责任

| 角色 | 运行范围与责任 |
| --- | --- |
| main | 全局唯一的 Nexus 入口，处理分诊、项目归属和上级处置，不被单个跨项目任务长期占住 |
| project | 每项目一个责任编排者，管理本项目队列、执行、验收及工作线阻塞 |
| supervisor | 按需建立的临时跨项目协调者，只负责关联工单的依赖与协调，不取代各项目编排者 |
| worker | 每票同一时刻最多一个活跃主执行，在该次执行的独立 worktree 中完成授权工作 |

main、project、supervisor 管理工作，不修改业务代码。worker 负责实现；管理者不能因 worker 故障或排队而亲自进入业务代码补做。

“每项目一个”是责任绑定唯一，不要求每个项目始终有模型回合运行。项目禁用或不可用后保留责任与历史，但不能据此继续派工。

Nexus 自有角色会话必须由宿主明确建立可恢复的账本绑定；身份来自该绑定，不来自 preset 名称、提示词、自报角色或消息正文。重启时也不得仅凭同名 preset 接管已有会话。

原生 DSH subagent、subagent_fork 与现有 sidechat 可以继承角色 preset，但不因此成为 Nexus 角色、取得主 Worker 授权或占据新主执行名额。侧聊继续保持现有权限行为，不另加只读限制。

worker 保留标准 DSH helper 的创建、继续对话、等待、打断和向父代理回报能力。helper 的执行仍属于原主工作线，不可被用来绕开工单授权或主执行唯一性。

原生 helper 保留原生工具和回报指引，不因 Nexus 的同名工具注册而丢失原生 send_message 行为。Nexus 角色父会话仍能继续联系自己的原生 helper；公共兼容入口由 03 定义。

关联票全部成功完成且无未决问题、依赖或故障时，宿主自动结束临时 supervisor；关联票 cancelled/失败不冒充全员成功，由 main 决定调整范围或关闭。不能只关闭会话就抹去未结协调责任；任何责任变更须有明确管理依据和可追溯去向。

## 派工、并发与工作区

建票、派工、暂停、恢复、取消、重试及协调范围调整是独立管理行为，不能由普通 send_message 的成功回执或正文指令隐含执行。管理入口沿用 01 的身份、项目范围和授权核验。

派工受理前必须确认项目仍启用且可用、工单授权仍成立、前置依赖已满足、没有人的暂停，并且不存在该票的另一个活跃主执行。受理结果与实际启动分别可见。

全局主执行并发遵循 01 的 maxWorkers；管理会话、helper 和侧聊不另计主执行名额。多个项目同时派工或同一事件重复唤醒，不能突破并发上限或生成重复主执行。

等待名额的票保留排队原因。一个项目的故障、投递失败或待答 ask 不应阻塞其他项目的事件处理与符合条件的派工；不以串行跑完一张票作为整个系统处理下一票的条件。

每次主执行使用独立 worktree，与其他票和管理者的工作目录隔离。会话、工单、项目、worktree 和仓库归属必须可核对，不能只依赖模型记住路径。

开始执行前确认 worktree 的仓库和分支归属；遇到已被占用、归属冲突或历史改动不能确认的工作区，报告可区分的阻塞，不静默复用、重置或删除。

暂停与取消应阻止新动作，并请求停止受影响的在途执行。停止请求已受理不等于旧执行已经结束；在旧执行仍可能写入时，不能释放同票唯一性并启动替身。

暂停保留继续工作所需上下文和工作区；取消也不承诺回滚已经发生的提交、PR 或其他外部操作。未提交改动和异常退出的 worktree 不能被自动清理以掩盖故障。

重试是明确的管理决定，不是重复收到事件就再 spawn。新执行前核对旧执行是否已停止、已有交付和外部副作用，避免重复建分支、PR 或再次完成同一动作。

人的暂停只由明确的人工恢复管理行为解除。评论、CI、正式答案、模型建议和提醒都可更新事实，但不能自动恢复该票；暂停期间仍可展示并处理其问题和通知。

项目禁用或失联时停止新派工与续跑，打断可停止的在途动作并保存收尾结果。已经送出的外部请求须核对实际结果，不能把禁用误报为远端回滚成功。

## 供 03 消费的运行行为契约

本节是运行能力边界，不规定工具字段、函数签名或存储布局。03 不能通过模型推测补齐这些事实，也不能另维护一份角色与会话归属。

### 角色寻址与责任核验

运行层提供宿主确认的当前角色、关联项目/工单、责任会话及其可用状态。未知、关闭、失联和存在绑定冲突必须可区分，不能静默选择同名会话。

逻辑角色的责任可以跨空闲与进程重启保持；会话不可用不等于其收件责任消失。03 可保留待投递内容，并依据运行恢复结果投向核实后的会话。

### 事件输入与处理反馈

运行层接收已由相应领域入口确认的消息、正式答案、ask 待处理、会话结束、工单/依赖变化、人工介入和提醒事件。GitHub 原始输入由 [04 GitHub 接入](./11-16-nexus-v1-github-design.md)负责，不由运行层重新解释授权。

事件须能关联持久来源、目标责任与相关工作线；人工介入显式标明来源，不能伪装成普通代理汇报。重复通知仍只对应原来的领域事实，不重复派工或执行副作用。

03 能区分事件已受理、已进入会话上下文和处理是否完成。只有实际进入上下文才可标记读入；会话正忙、已关闭或唤醒失败不能虚报已读。

同票同收件责任的事件保持 01 要求的顺序；无需把所有工单串成一条队列。答案先于唤醒落账时，恢复后仍消费已有答案，不要求回答者重答。

### 工作线挂起与恢复

03 建立 pending ask 后，运行层挂起依赖该答案的工作线，并让同一编排者继续处理其他票或无关工作。不得长期占住编排者整个回合等待一个答案。

该能力不依赖原生 ask_user_question，不以调用会话是 DSH live root 为前提；ask 的持久生命周期由 01、03 承担，不能把原生工具调用的存活时间当作问题寿命。

挂起关联原 ask 与工作线，不复制工单或生成新的主 Worker。正式答案事件使该线具备续接依据，但继续动作前仍核验人的暂停、项目可用性和当前授权。

被中断的工具等待可以结束为“仍待处理”，并保留未决对象及原因。03 不能把工具返回、回合结束或恢复成功解释为 ask 已回答。

### 唤醒与故障反馈

运行层对可用责任会话投递事件，空闲会话被唤醒，繁忙会话按中断规则接入。无法唤醒时反馈可恢复失败或需人工处置的原因，并保留原消息、ask 和责任。

已关闭会话不能作为可续接对象使用。恢复是否需要新会话由下述核对结果决定，不由 03 每次投递失败自行创建新角色会话。

## 所有工具的异步与中断语义

所有工具均须异步执行并响应宿主中断，包括 wait、ask、管理操作、工作执行及外部调用；不可打断的底层请求不能成为无限占住回合的理由。

中断停止本次继续等待或后续动作，不保证撤销已送达远端的请求。已知成功保留结果，已知失败保留原因，结果未知先进入核对，不盲目重做。

会话结束、待处理 ask、人工介入、新渠道消息与提醒到期可打断编排者的 wait/ask，使其转入事件处理。被打断的原问题和待办继续存在，不视为取消、批准或完成。

普通进展消息排入 worker 上下文，不自动取消实际工作。只有明确止损需要或人的明确要求才打断该执行；“所有工具可打断”不等于所有消息都触发停止。

Nexus 管理取消与原生 interrupt_agent 保持独立于 send_message。打断原生 helper 或某个模型回合不等于取消工单，也不等于撤销它已发起的 ask。

显式撤销 ask 由 03 按 01 的合法来源与生命周期处理。运行层不得以工具 abort、超时、断线或主 Worker 退出替代这一决定。

后台运行预算沿用 01 的配置。预算到期形成可观察的中断或待处置事实，保留未完成责任与待核对结果，不自动结票、批准、取消或重试。

## idle、closed 与责任持续性

idle 表示当前没有模型回合运行，不表示工单完成或无需处理事件。有未结责任的编排者允许 idle，宿主必须仍保有可定向唤醒的责任绑定与提醒依据。

closed 表示原会话不能继续使用，不表示其工单、ask、消息或依赖已结清。运行层保存关闭原因和未结责任，进入恢复或上报，不向关闭会话虚假投递。

正常无待办退出、主执行结束和异常关闭应可区分。worker 自报完成或 DSH settlement 只是执行事实，交付验收及工单 done 仍由 01 的规则决定。

管理者没有活跃回合时，系统仍能接收工单事件并触发宿主提醒。“有任务不退出”落实为责任持续保留，而不是让模型持续输出 wait。

## 事件驱动与宿主提醒

消息、答案、状态与依赖变化是正常唤醒来源；提醒由宿主时间能力触发，不要求模型反复调用 wait、list 或读库轮询。重启后从持久等待事实恢复提醒，不从零重新计时掩盖停滞。

提醒周期使用 01 的 reminderIntervalMinutes，默认 10 分钟。计时针对相应等待或执行的最近有效进展；模型空回合、重复读取、通知已受理不算有效进展。

超过周期没有进展，先向当前责任编排者发出提醒。提醒包含原工单/ask 或执行关联、等待对象、已经等待多久、最近已知近况和当前阻塞原因。

提醒必须留下可观察的产生时间、目标责任和投递结果。目标会话不在线不算已处置；投递失败保留待投和失败原因，不能默默跳过第一责任方。

“已经提醒责任方”与“责任方已经处置”分别可见。处置应有可关联的续接进展、合法继续等待依据、恢复结果或明确的无法恢复原因；只读消息不算处置。

在责任方已获提醒后，到下一提醒周期仍没有上述处置，向 01 规定的既定上级链报告停滞；若责任方已明确无法恢复，可不等下一周期即上报。责任方无法送达时也须保留先行提醒尝试及失败依据再升级。

升级通知关联同一等待责任和已有证据，不自动取消执行、批准问题、解除暂停或转移原 ask 的当前处理者。需正式移交问题时由 03 按 01 显式办理，不把提醒投递当成移交。

已经明确在等人的 ask，只围绕原 ask 提醒并展示等待时长，不创建第二个批准问题，不把人的未回答判成代理失职，也不让上级代替必须由人给出的答案。

同一停滞原因的重复提醒归并可追溯，不靠反复建票、建 ask 或创建会话吸引注意。有效进展改变等待依据后，后续提醒展示新近况，但不伪造旧问题已经完成。

人的暂停持续显示为主动暂停；暂停本身不触发自动续跑或无意义的故障升级。暂停期间真实出现的待答问题、外部结果和恢复故障仍保留各自可见性。

## 中断后的恢复核对

宿主启动或会话异常后，先读取 01 的工单、角色、未处理消息、ask、暂停和责任事实，再核对实际 DSH 会话、worktree 与 GitHub 状态。核对未完成前不自动重做写操作。

会话核对要区分仍在执行、可继续、已关闭和无法确认；worktree 核对仓库归属、分支、已有改动与占用；GitHub 核对相关 issue/PR、head、合并及在途操作结果，事实来源与投递由 04 承接。

原会话和工作区可用时优先续接，只补入尚未消费的事件。不能因模型暂时无回复、页面断线或提醒到期反复 spawn。

只有确认旧主执行不再活跃且无法原位继续，才可在合法管理决定下建立替代会话；新旧绑定与恢复原因可追溯，同票不出现两个可能同时写入的主执行。

外部写操作结果不明时先核对关联。PR 已创建、答复已落账、远端已合并或原任务仍在运行，都不能因为本地缺少回执而重复发起。

部分依赖暂不可用时保留待核对状态与最后已知事实，不把“没查到”解释为“从未发生”。无法自动恢复时明确告知责任方原因、保留资产与需要人作出的决定。

恢复不能覆盖人的暂停、撤销已生效的取消或绕过当前工单策略。恢复成功只说明运行可继续，不说明验收成功，也不补造历史批准。

## 错误与可观察结果

未知角色绑定、越权管理、项目禁用/失联、主执行冲突、并发排队、工作区冲突、会话关闭、工具中断和远端结果不明应可区分。拒绝操作不得留下半次派工或隐含授权。

管理请求至少能区分已受理、实际执行中、已结束与需要核对；不会把停止请求回执当成旧执行已经停止。持久化或调度失败显式报告，不用空状态冒充无待办。

[05 Web 编排面板与信箱](./11-16-nexus-v1-web-design.md)消费上述运行事实，展示当前责任、近况、等待原因、提醒与恢复失败；运行层不另造一套面板专属业务状态。

## 独立验收与验证范围

局部验证使用真实领域账本与隔离工作目录，外部会话和渠道边界可用受控替身；测试的是实际运行行为，不以工具名称或提示词快照代替。

本 Spec 可在 01 完成后独立实现与验证；04 的网络连接和 03 的工具实现不是本模块开发前提。局部验证提供符合领域契约的事件与远端事实输入，不另造共享协议，真实接线交 06 核验。

- 并发派工、重复事件和恢复竞争下，main/项目责任唯一，每票只有一个活跃主执行，主执行数不超过 01 上限。
- 多项目工单独立推进；一票 pending ask 挂起相关工作线，同一 project 仍可处理另一票及新事件。
- 管理者不改业务代码；worker 工作区隔离，暂停/取消/失败不破坏历史改动，不在旧执行未停时启用替身。
- 原生 helper 和 sidechat 即使同名 preset 也不取得 Nexus 角色绑定；helper 保持原生收发、回报和完成通知，父会话能继续对话。
- 每类工具的中断都有可观察结果；wait/ask 打断后未决对象保留，普通进展不自动停止 worker，远端结果未知不盲重试。
- idle 能由事件唤醒，closed 进入恢复；会话结束、自报完成和后台预算到期均不能直接完成工单。
- 受控时间下验证先提醒责任方、仍无处置再上级、无法恢复可及时上报；提醒目标、时间、关联与失败原因完整可查。
- 已等人只提醒原 ask，不生成新问题或转移答案责任；暂停收到答案、CI、评论和提醒后仍不自动续跑。
- 重启核对会话、worktree、GitHub 后续接；重复恢复不重复 spawn、建 PR、发答案或重做已有远端副作用。
- 注入关闭会话、失联项目、工作区冲突与存储失败，责任和待办不丢，03 能取得可区分的运行反馈。

局部测试及真实 DSH 验证的记录、执行环境和证据归档由 [06 宿主装配与真实验收](./11-16-nexus-v1-integration-design.md)承接。06 须在当前可用 DSH 验证角色会话、原生 helper、真实中断、提醒与重启续接，不将受控替身通过视为真实集成已通过。

本 Spec 的通过只证明运行编排边界；问答鉴权、GitHub 真实投递和 Web 交互需各自子 Spec 及 06 的整体验收，不声称单模块证明整套系统。
